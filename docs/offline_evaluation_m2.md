# M2 统一离线评价口径

本入口评价现有两段开发视频的四组保存结果，不运行检测/跟踪，不修改外观核心、阈值或状态。它完成评价工具交付，不代替 00 的范围、冻结或 M3 决策。旧 `evaluation.json` 保留，但其中按算法丢失次数计算的 `unrecovered_events`、固定待输入与整体验收字段不参与新汇总。

## 运行与输出

在项目根目录、沿用已有 `.venv`：

```bash
.venv/bin/python scripts/evaluate_offline.py --protocol configs/m2_evaluation.json --output outputs/m2_evaluation_v1
.venv/bin/python -m unittest discover -s tests -v
```

复跑须换成空的新目录，例如 `outputs/m2_evaluation_v2/`；非空目录在读取输入前就拒绝覆盖。无需 GPU 或新依赖，需要本地视频、旧输出、独立标注和 Git 历史对象。输入缺失、SHA/次数/区间不一致时报错，不生成假结论。脚本退出码 0 表示核查与评价完成，报告内的 FAIL（例如 f180）仍表示算法行为失败。

| 文件 | 内容 |
| --- | --- |
| `configs/m2_evaluation.json` | 两个独立人工事件、半开评价窗、旧标注路径/SHA、共享开关组、历史提交；这是开发评价适配记录，不是冻结恢复参数 |
| `protocol.json` | 此次协议原样副本 |
| `per_event_results.json` | 四组逐事件身份、期待返回、程序接受、延迟、误报与候选覆盖证据 |
| `summary.json` | 四组汇总、范围状态、标注限制和未验证事项；不合并重复开关组制造更多独立事件 |
| `candidate_coverage.jsonl` | 全程及人工替代瓶子区间的逐帧检测/候选分类与数量；范围字段区分两个分母 |
| `source_checks/` | 各组对应 Git 快照的记录/视频核查，关闭组 TargetState 回放，开启负例原像素重算报告 |
| `run_info.json` | 准确命令、评价脚本/协议 SHA、每组原命令、输入/标注/历史代码校验与证据来源 |
| `preservation_before.json` / `preservation_after.json` | 所有既有输出、核心脚本/配置和原视频的 SHA 保全清单 |

## 独立事件与身份

开关组共用同一 `episode_id`、物理身份、`expected_return`、评价窗和旧标注。每组单独评价同一个事件，而非把四组计成四次独立拍摄。`algorithm_confirmed_losses` 从逐帧确认丢失帧集合重算，只是算法诊断；`confirmation_attempts` 来自计数开始事件；二者都不能充当返回机会分母。

- `tabletop_02_cardboard_return_1`：用户确认“遮挡期间只移动了原瓶子，没有替换”。人工期待返回 1 次；评价窗 `[600,984)` 覆盖人工初始化至片尾的后半段纸板事件，不声称精确标注了遮挡起止。可辨认重现 f847、接受 f852 的身份与人工框来自旧独立记录。程序接受帧须匹配人工 T1 且框 IoU>=0.5 才计正确。缺少身份/框依据的接受记未评价，不能计正确或零错误，也不能断言该事件一定未恢复。
- `wrong_bottle_replacement_1`：用户确认换成另一只瓶子，原瓶子未再入镜。评价窗 `[0,633)` 覆盖整片唯一替换事件；期待原目标返回机会为 0。原目标恢复成功率和延迟不适用；没有接受不能写成一次恢复失败。人工清楚可见替代瓶子区间保持旧记录的 `[485,633)`，即 f485—632 共148帧，不把终点改为632或算法首次检测484。

身份与边界依据来自原画面和拍摄者确认，不来自原生 ID、检测分数、外观分数或程序丢失/接受。旧标注通过适配读取，原文件/SHA不变。正例时间/框为 Codex 画面核对、尚非用户逐帧标注；负例框是固定人工空间区域与关键帧核对，非148个逐帧精确框。接受帧核对不扩大可见控制采样分母。

## 指标与状态

| 项目 | 口径 |
| --- | --- |
| 正确恢复/未恢复 | 分母为人工明确期待返回的事件；有独立正确接受则该事件恢复，否则没有不明接受时记未恢复；不明接受单列 `unevaluated_return_events` |
| 正例延迟 | 正确接受帧减人工可辨认重现帧；分别保存原帧差、原帧差/名义FPS及源时间字段差。不成功或没有机会时用null与NOT_APPLICABLE，不写0秒 |
| 错误绑定 | 接受帧人工为其他实体、原目标已取走或恢复框不匹配时计错误；缺标注接受单列未评价。0接受可证明没有自动绑定，不能证明核验能力 |
| 错误当前位置 | 仅在独立确认原目标不在画面的标注区间内数当前框/已知位置；当前负例148帧。全片位置准确率未评价 |
| 替代瓶子覆盖 | 独立人工ROI与检测框IoU>=0.5，匹配须唯一；区分无匹配检测、检测但未成为候选、质量暂缓、证据不足和质量合格候选；无检测/低质不能算外观拒绝 |
| 外观拒绝 | 质量合格、有同一最佳参考且门槛确实失败才计拒绝；字符串须与证据一致。帧计数与候选观察数分开，多个候选可占同一帧；148帧属于一次替换事件，全程149候选另列 |
| 关闭组 | 保留检测/候选覆盖与不绑定结果；未执行外观质量与身份核验，合格/外观拒绝数量为null、状态NOT_APPLICABLE，不能算核验通过 |
| 可见UNKNOWN | 仅针对独立可见控制点，从 `position_known` 判断，不以TRACKING主状态掩盖未知位置。当前只有负例f180；全片可见/遮挡区间未补齐，整片误报率为null/UNEVALUATED |

`PASS`＝在明确证据范围满足该项；`FAIL`＝有明确失败证据；`UNVERIFIED`＝未取得所需真实输入/独立依据；`NOT_APPLICABLE`＝该事件无机会或该组无此机制；`UNEVALUATED`＝当前标注/覆盖不足。不同项目分列，不能把一个PASS升级成全项目通过，不能把未评价当作0错误。

## 历史来源核查与保全

开启正例使用提交 `3163e39`、开启负例使用 `3e557e6`、两组关闭v2使用 `a167bba`。入口先逐文件对比旧 `run_info.code_sha256` 与该 Git 对象内容，再导出当时脚本至临时目录。记录/视频核查只在临时副本写报告；旧输出只读，原SHA不修改，当前代码不替代历史代码，也没有跳过来源检查。

四组重新核查原生记录、时间、参考/裁剪、配置/视频 SHA、状态/事件、视频解码；两组关闭分别由当时 TargetState 回放全部384/633帧。新入口从记录重算状态、确认丢失、接受/尝试/事件与候选判定次数并核对汇总。开启负例用历史专项验证器重新解码原视频，重算148帧外观质量与最佳参考分量；旧专项PASS本身不作为新证据。该专项重算复用历史外观核心，04已有的独立分量重算为补充历史证据；本轮未重跑04全套独立审查。

同时校验04旧输出保全清单、统计修复引用的04证据SHA、两组新关闭run_info/review的SHA，并保全任务前后所有旧输出/核心/原视频。临时历史报告的旧身份评价字段不用于统一指标；新指标只来自独立事件和实际记录。
